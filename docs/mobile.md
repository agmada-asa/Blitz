# Blitz Android app

The Android client lives in `mobile/` as an independent Expo project. It uses
Expo SDK 57, React Native 0.86, and React 19.2. The mobile lockfile is kept
separate from the browser app's root lockfile so native tooling can evolve
without changing browser dependencies. The native surface mirrors the web
app's core screens: the prepared learning feed, project library and workspace,
workspace chat, activity, settings, source management and preview, research
planning, practice, tests, and written activities. The icon-only bottom
navigation keeps Home, Library, Chat, Activity, and Settings in the native
stack; project links from Activity open the matching native destination.

The app identity is configured as `Blitz` with the local Android application
ID `com.blitz.study`. This is a development identity only; no signing keys,
Expo account, EAS project, or release credentials are required or checked in.

## Prerequisites

Expo SDK 57 currently requires Node.js 22.13.x or newer. The versioned Expo
Android guide recommends JDK 17. Android builds use compile and target SDK 36.
Install Android Studio's Android SDK Platform 36, SDK Build-Tools 36.0.0, and
platform-tools. Define `ANDROID_HOME` for the shell used to build and ensure
`adb` is on `PATH`.

On macOS, the build commands below select JDK 17 without changing the user's
global shell configuration:

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
```

The source for these requirements is the [Expo SDK 57 reference](https://docs.expo.dev/versions/v57.0.0/), the [Expo Android emulator guide](https://docs.expo.dev/workflow/android-studio-emulator/), and Android's [SDK Manager documentation](https://developer.android.com/tools/sdkmanager).

## Install and run

From the repository root:

```sh
cd mobile
npm ci
npm run start
```

Use the Expo CLI development server with a connected Android device or Expo
Go. To generate the local native project and install a debug build on an
available device or emulator:

```sh
cd mobile
npm run android:debug
```

The native `android/` directory is generated by Expo prebuild and ignored by
Git. Run `npm run prebuild:android` when you need to inspect or regenerate it.

When no server URL is configured, the app presents a connection field. Set
`EXPO_PUBLIC_BLITZ_URL` before starting Metro or enter the LAN address in the
app; no private machine address is embedded in the bundle. The feed uses
vertical full-screen paging, recap cards, every question format, project
filters, and an `Ask in chat` sheet backed by the server's persisted chat
queue. Source imports
can be uploaded from the Android document picker or added as pasted notes and
public links. The native `Library` control opens searchable modules with their progress.
Select one to open its learning path and practice (see below).

## Teach, Practice, and Home on the phone

The phone runs the same learning loop as the desktop, on the contracts in
`lib/learning/mobile-contracts.ts` (served by `app/api/mobile/*` through
`lib/server/mobile-learning.ts`):

- **Home** opens on the Today page (`components/today-page.tsx`, from
  `GET /api/mobile/home?tz=`): the streak, today's XP against the goal, the
  last seven days, and a Continue card for the unit being learned with its
  section bar. Swiping up gives the feed (`GET /api/learning/feed`), which
  renders every question format: single choice, multiple answer, true or
  false, cloze, ordering, matching, and code output
  (`components/question-view.tsx`). Formats the app does not know are skipped
  rather than failing the feed.
- **Library** lists modules with one bar segment per unit and "N of M units
  taught · Next: …", most recently studied first (`GET /api/mobile/modules`).
  Opening a module shows its page (`components/module-screen.tsx`,
  `GET /api/mobile/modules/[projectId]`): the unit to continue, the learning
  path drawn as a path with each unit's section bar, a drill card with the
  concept mastery bar, concepts that are not sticking with Relearn, and the
  exam papers (sat on the computer). Sources, files, and research are one tap
  away in the older project workspace.
- **Teach** (`components/teach-screen.tsx`) opens a unit's session
  (`POST /api/mobile/teach` creates it on first visit) and starts teaching
  straight away. Turns are sent to the shared `/api/chat` route; while the
  tutor writes, the screen re-reads the saved reply from
  `GET /api/mobile/teach?unitId=` every 1.2 seconds, as the desktop reads it
  from the database. Replies are split into Markdown and interactive blocks
  (`lib/teach-content.ts`): quizzes are answered natively and recorded through
  `/api/teach/answer`, worked examples reveal step by step, follow-ups send a
  question, and visualisations point to the computer. Formulas are shown as
  readable Unicode (`lib/math-text.ts`), citations as labels. The header has
  the section bar, XP this sitting, and Finish, which opens the session
  summary. A Relearn request from Practice is sent once when the session is
  ready.
- **Drills** (`components/drill-screen.tsx`, `GET /api/mobile/drill`) ask ten
  questions, missed and weak material first, as feed cards without answer
  keys; `/api/learning/answer` scores each one and reveals the key. A miss
  offers Relearn. The drill ends with the session summary
  (`GET /api/mobile/summary`).

## Offline

Everything the learner has opened is kept on the device
(`lib/offline-cache.ts`, scoped to the server URL): the Today page, the
library, module pages, drill decks, and the last 30 lessons. Without a
connection these are shown with an offline notice. Lesson quizzes answered
offline are graded from the lesson's own quiz block and queued; the queue is
recorded the next time a lesson opens online. Drill answers use the feed's
event queue, so they sync with the feed. New teaching needs the computer,
because the tutor runs there.

## Older native screens

Chat, Activity, and Settings use the same server contracts as the web
screens. The project workspace (sources, generated files, research) and its
older study, test, and writing tools remain available from a module's
**Sources and files**. Source preview keeps the web overview's metadata,
extracted text, status, retry, and original-file actions. Research keeps the
web approval boundary: suggested sources are never imported until the
learner selects them explicitly.

## Build a debug APK without a device

The ordinary `expo run:android` debug build is Metro dependent. To build an
installable local preview that embeds the JavaScript bundle, use the checked-in
script below. It uses Expo prebuild, asks the React Native Gradle plugin to
bundle the debug variant, signs with the generated local debug keystore, keeps
the debug manifest's cleartext LAN access, verifies `assets/index.android.bundle`
inside the APK, and removes only the native directory it created afterward. It
refuses to run when `mobile/android/` already exists, protecting an inspected
or user-maintained native project:

```sh
cd mobile
./scripts/build-debug-preview.sh
```

The generated native directory and APK build output are not committed. The
script writes the preview to `build/android/blitz-android-debug.apk` at the repository root by
default; set `BLITZ_ANDROID_ARTIFACT_DIR` to choose another local output
directory.

The output directory is ignored by Git and survives temporary-directory cleanup.

## Shared learning module

The native adapter imports the framework-independent
`lib/learning/client-contracts.ts`; the same Metro boundary also permits
plain consumers of `lib/learning/core.ts` through the watched repository root.
`mobile/metro.config.js` follows Expo's SDK 57 Metro configuration shape,
watches the repository root, and keeps dependency resolution anchored to
`mobile/node_modules`. The adapter sends exactly the shared route fields:
`projectId`, `itemId`, `clientEventId`, `occurredAt`, and `answer` for answers;
`projectId`, `itemId`, `clientEventId`, `occurredAt`, and `eventType` for skip
and exposure events. Server answer fields are withheld from feed cards and
correctness is displayed only after the answer response arrives.

Prepared cards are cached in AsyncStorage with a 60-card cap, scoped to the
normalized server URL. The feed requests 20 cards at a time and follows the
server's opaque `continueCursor`, appending each page by card ID. Refreshing the
same feed preserves loaded pages while the app is running. A fresh launch replaces
the restored cache when its first online response arrives.
Answers, skips, and exposures are queued with stable UUID client event IDs and
a 200-event cap; queued events are retried in order when the same server is
reachable. Queues are scoped to that server, so changing servers never sends
old events to the new endpoint. Legacy global data is migrated only when the
previously saved server URL identifies its owner; otherwise it remains
preserved and unassigned.
At the cap, passive events can be dropped, but unsynced answers are retained.
If the queue contains 200 answers, new answers wait until sync frees space.
An offline answer is labelled as saved while waiting for sync and is never
presented as correct or incorrect locally. Project and topic filters are also
applied to cached cards locally when the server is unavailable, and topic
choices are limited to the selected project. A card locks after a server answer
response so a revealed explanation cannot create repeated answer evidence. On
restart, queued answer events restore that pending lock for cached cards; skip
and exposure events never create answer feedback.

The native chat sheet uses `GET /api/learning/chat?projectId=…&itemId=…` for
the conversation, `POST /api/learning/chat` with `projectId`, `itemId`,
`clientMessageId`, and `question` to queue a learner message, and
`POST /api/learning/chat/retry` with `projectId`, `itemId`, and `messageId` to
retry a failed message. It subscribes with `stream=1` while open, renders partial replies as Markdown, and reconnects to saved history after network loss. A failed
network send leaves the learner's text and stable client message ID in the
sheet so retrying cannot create a duplicate question.

## Morning interaction fixes

Server-scored answers now color every correct option green and each selected
mistake red. Pending offline answers stay neutral. Chat shows queued or preparing
reply status with elapsed time refreshed by its existing polling.

Feed paging recognizes shorter vertical drags and quick flicks. The distance
threshold is 3% of the logical viewport height, bounded to 24–48 points.
Paging starts from the index captured at drag begin and clamps the target to one
adjacent card. Vertical intent uses the larger displacement from touch or native scrolling.
Android can stop raw touch updates when its scroll view takes over, so a partial
touch movement must not replace a larger native scroll distance. Horizontal
intent uses touch coordinates. The page change runs on the
next animation frame after drag end. The native scroll view uses interval
snapping and fast deceleration. At momentum end, it corrects a native snap that
landed on a different page. Android can emit a second completion after the
programmatic animation, so the target survives both completions. A new touch,
filter change, refresh, or explicit Skip cancels that target. Card contents enable their inner scroll view
only when measured content exceeds its viewport, so fitting cards do not
consume the feed swipe. Overflowing cards retain nested scrolling and Skip.

The mobile unit suite now has eight tests, including gesture thresholds,
horizontal rejection, direction, and boundary clamping. TypeScript passes.

The final clean APK was installed on the task-owned API 35 emulator at
1080 × 2400, density 420. The primary agent verified 100-pixel, 800 ms swipes
forward and backward over card content, followed by 500-pixel swipes in both
directions. Each moved exactly one card. Earlier candidates snapped back;

The verified APK embeds 1,248,988 bytes of Hermes JavaScript and contains no

## Native library and feed polish

The native library uses `GET /api/projects` for metadata and `POST /api/projects`
for explicit create, rename, and delete operations. The route validates names and
IDs and reuses the browser's Convex mutations. Browser-origin requests must come
from this server; native requests have no Origin header. Management requires a
connection and does not queue mutations offline. A timeout asks the learner to
refresh before retrying, since a server may have completed the operation.

Deleting a project removes its cached cards, filter metadata, and pending events
from this device after server confirmation. Other projects and their queued
answers stay intact. The server's existing atomic deletion limit still applies;
oversized deletions leave all records intact and report an error.

The feed has native coral and blue radial backgrounds and scroll-driven card
opacity/translation. React Native's existing renderer and Animated native driver
handle this without another package. Background motion stops while the app is
inactive or a sheet is open. Device reduced motion disables both background and
card animation. Existing single-card paging and nested content scrolling remain.
