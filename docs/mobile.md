# Blitz Android app

The Android client lives in `mobile/` as an independent Expo project. It uses
Expo SDK 57, React Native 0.86, and React 19.2. The mobile lockfile is kept
separate from the browser app's root lockfile so native tooling can evolve
without changing browser dependencies. The current native surface is the
full-screen prepared learning feed; wider native library and import flows remain
outside this bounded integration.

The app identity is configured as `Blitz` with the local Android application
ID `com.blitz.study`. This is a development identity only; no signing keys,
Expo account, EAS project, or release credentials are required or checked in.

## Prerequisites

Expo SDK 57 currently requires Node.js 22.13.x or newer. The versioned Expo
Android guide recommends JDK 17. Android builds use compile and target SDK 36.
Install Android Studio's Android SDK Platform 36, SDK Build-Tools 36.0.0, and
platform-tools. Define `ANDROID_HOME` for the shell used to build and ensure
`adb` is on `PATH`.

On macOS, the build commands below select JDK 17 without changing the user's
global shell configuration:

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 17)"
export ANDROID_HOME="$HOME/Library/Android/sdk"
export PATH="$ANDROID_HOME/platform-tools:$PATH"
```

The source for these requirements is the [Expo SDK 57 reference](https://docs.expo.dev/versions/v57.0.0/), the [Expo Android emulator guide](https://docs.expo.dev/workflow/android-studio-emulator/), and Android's [SDK Manager documentation](https://developer.android.com/tools/sdkmanager).

## Install and run

From the repository root:

```sh
cd mobile
npm ci
npm run start
```

Use the Expo CLI development server with a connected Android device or Expo
Go. To generate the local native project and install a debug build on an
available device or emulator:

```sh
cd mobile
npm run android:debug
```

The native `android/` directory is generated by Expo prebuild and ignored by
Git. Run `npm run prebuild:android` when you need to inspect or regenerate it.

When no server URL is configured, the app presents a connection field. Set
`EXPO_PUBLIC_BLITZ_URL` before starting Metro or enter the LAN address in the
app; no private machine address is embedded in the bundle. The feed uses
vertical full-screen paging, explanation cards, single-choice,
multiple-answer, and true/false questions, project/topic filters, and an
`Ask in chat` sheet backed by the server's persisted chat queue. Source imports
remain in the web library; the native `Library` control opens that route.

## Build a debug APK without a device

The ordinary `expo run:android` debug build is Metro dependent. To build an
installable local preview that embeds the JavaScript bundle, use the checked-in
script below. It uses Expo prebuild, asks the React Native Gradle plugin to
bundle the debug variant, signs with the generated local debug keystore, keeps
the debug manifest's cleartext LAN access, verifies `assets/index.android.bundle`
inside the APK, and removes only the native directory it created afterward. It
refuses to run when `mobile/android/` already exists, protecting an inspected
or user-maintained native project:

```sh
cd mobile
./scripts/build-debug-preview.sh
```

The generated native directory and APK build output are not committed. The
script writes the preview to `build/android/blitz-android-debug.apk` at the repository root by
default; set `BLITZ_ANDROID_ARTIFACT_DIR` to choose another local output
directory.

The output directory is ignored by Git and survives temporary-directory cleanup.

## Checks

Run the app-local checks from `mobile/`:

```sh
npm run test
npm run typecheck
npm run doctor
npx expo export --platform android
```

`expo export --platform android` is the Metro bundling check. It verifies that
the app entrypoint and the shared learning module can be bundled without
requiring an attached device.

## Shared learning module

The native adapter imports the framework-independent
`lib/learning/client-contracts.ts`; the same Metro boundary also permits
plain consumers of `lib/learning/core.ts` through the watched repository root.
`mobile/metro.config.js` follows Expo's SDK 57 Metro configuration shape,
watches the repository root, and keeps dependency resolution anchored to
`mobile/node_modules`. The adapter sends exactly the shared route fields:
`projectId`, `itemId`, `clientEventId`, `occurredAt`, and `answer` for answers;
`projectId`, `itemId`, `clientEventId`, `occurredAt`, and `eventType` for skip
and exposure events. Server answer fields are withheld from feed cards and
correctness is displayed only after the answer response arrives.

Prepared cards are cached in AsyncStorage with a 60-card cap, scoped to the
normalized server URL. The feed requests 20 cards at a time and follows the
server's opaque `continueCursor`, appending each page by card ID. Refreshing the
same feed preserves loaded pages while the app is running. A fresh launch replaces
the restored cache when its first online response arrives.
Answers, skips, and exposures are queued with stable UUID client event IDs and
a 200-event cap; queued events are retried in order when the same server is
reachable. Queues are scoped to that server, so changing servers never sends
old events to the new endpoint. Legacy global data is migrated only when the
previously saved server URL identifies its owner; otherwise it remains
preserved and unassigned.
At the cap, passive events can be dropped, but unsynced answers are retained.
If the queue contains 200 answers, new answers wait until sync frees space.
An offline answer is labelled as saved while waiting for sync and is never
presented as correct or incorrect locally. Project and topic filters are also
applied to cached cards locally when the server is unavailable, and topic
choices are limited to the selected project. A card locks after a server answer
response so a revealed explanation cannot create repeated answer evidence. On
restart, queued answer events restore that pending lock for cached cards; skip
and exposure events never create answer feedback.

The native chat sheet uses `GET /api/learning/chat?projectId=…&itemId=…` for
the conversation, `POST /api/learning/chat` with `projectId`, `itemId`,
`clientMessageId`, and `question` to queue a learner message, and
`POST /api/learning/chat/retry` with `projectId`, `itemId`, and `messageId` to
retry a failed message. It polls every three seconds while open. A failed
network send leaves the learner's text and stable client message ID in the
sheet so retrying cannot create a duplicate question.

## Install over the local network

Set `BLITZ_ANDROID_APK_PATH` to the absolute path of a built `.apk` when starting
Blitz. `GET /api/android` streams that file as an Android package download;
without a configured artifact it returns 404. The route never accepts a path
from the request and the APK is never committed.

The overnight build's LAN download was streamed and SHA-256 checked against the
artifact above. Installing and visually testing it on a physical phone remains
unverified.
