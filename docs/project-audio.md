# Project audio

Blitz can narrate a ready source as an audiobook or write a podcast from the ready sources in a project. Both features run Kokoro on the Mac hosting Blitz. Chat's **Read aloud** action uses the same local speech worker and the first voice saved in Settings.

## Voices and setup

Settings offers five Kokoro voices with short previews. Users save one or two voices in order. The first narrates audiobooks and chat replies. Podcasts use one host when one voice is saved and alternate between two hosts when two are saved. Voice IDs are validated at the route and Convex boundaries.

Run `scripts/setup-kokoro.sh` once on the Mac. [Local Kokoro setup](local-kokoro.md) covers the Python environment and model download. The worker keeps the model loaded between requests, so a long recording submits short sections through the same queue used by chat playback. Active read aloud requests take priority between sections of a long job. The player prepares only the opening of the active lesson or latest reply and schedules later sections during playback. [Read aloud latency](local-kokoro.md#read-aloud-latency) describes preparation, cancellation, and cache limits.

## Generation

- An audiobook sends a ready source to the configured **Research** model in bounded, ordered sections. For project-local PDFs, it first re-reads the original file with position-aware text ordering, so improved extraction also applies to older imports. Otherwise it uses the saved `extractedText`. The model makes a light spoken edit, restores sentence flow, skips page furniture and access codes, and flags names, technical nouns, and acronyms that need phonetic speech spellings. It may describe a diagram or image only when extracted text includes a useful caption, label, or alt text; this path does not inspect image pixels. The original source remains unchanged. This preparation uses provider credits.
- A podcast first sends project source text to the configured **Research** model. Large projects are summarized in bounded source sections before the model writes an outline and five-minute script sections. Podcast turns use the same spoken-word and pronunciation guidance as audiobooks, including instructions to skip page furniture, access codes, and unsupported visual details. Source text and the optional focus are treated as data, and each section must pass a dialogue and word-count check before speech starts. This means podcast creation can use provider credits even though speech is local.
- Podcast length choices are 15, 30, 60, and 90 minutes. The final length depends on the selected voices' speaking pace; the saved item reports measured audio length after generation.

`POST /api/projects/[projectId]/audio` starts a background job. `GET` on the same route lists its state. The browser polls while a job is active and shows the current stage; recording progress is measured in completed speech chunks. Audiobook scripts retain page and slide boundaries, and the WAV joiner adds a short silence between them without speaking their numbers. New scripts and timed transcripts save both ordinary reader-facing text and the speech spelling sent to Kokoro. The listening room and passage questions use ordinary text; Kokoro receives the phonetic version. Known acronyms such as `AI` have locally checked defaults that override model suggestions, and model-supplied pronunciations stay consistent across later sections. Older transcripts without a speech spelling remain readable. Manifests, timed transcript JSON, saved script JSON, and completed WAV audio live under the project's `Audio/<id>/` directory. `/api/projects/[projectId]/audio/[audioId]/file` serves completed audio with byte ranges for seeking. The WAV download is uncompressed, so long episodes can use substantial disk space.

The listening room at `/projects/[projectId]/listen/[audioId]` follows the timed transcript during playback and can seek to any passage. WAV part lengths are measured, then the shorter displayed passages receive approximate times within each part based on their speech text length. Users can ask about the current passage or select up to twelve passages. Both actions pause playback and open the same Ask Blitz panel used by the learning path, beside the transcript on desktop and full screen on mobile. The selected reader-facing text, speaker labels, and timestamps attach to a new project chat through `/api/chat`; the full recording and project sources are not attached. The shared composer supports streaming replies, model settings, and source citations. Selecting different passages starts a fresh draft. After the first message, the conversation is saved in project chat history and remains available after closing the panel. Questions use provider credits.

The listening room saves each recording's playback position in the browser's local storage, keyed by project and recording. It restores the time after audio metadata loads and updates the transcript without starting playback. Time updates, seeks, pauses, page hides, and leaving the room save the position. When a recording finishes, its saved position is cleared so it opens at the start next time. Positions stay in that browser and do not sync across devices. If local storage is unavailable or its value is malformed, playback continues without resume data.

Only one audio job per project starts at a time. A job interrupted when the local host exits is marked failed when the app next reads it; the user can create it again. Failed jobs retain their error so the interface can explain the recovery step. Source files and generated audio use the existing ignored project data directory, or `BLITZ_DATA_DIR` when configured.
